# Engine API (`/v1/mask`, `/v1/unmask`)

Отдельная поверхность для тех, кто использует движок маскирования **как
компонент**, а не как прокси. Вызывающий шлюз сам владеет аутентификацией,
маршрутизацией, бюджетами и логированием: он просит замаскировать текст,
форвардит его сам, а потом просит восстановить оригиналы в ответе модели.

```
POST /v1/mask    →  замаскировать тексты, запомнить состояние под correlation_id
POST /v1/unmask  →  восстановить оригиналы по тому же correlation_id
GET  /v1/engine/version  (без авторизации)
```

Зачем отдельный листенер: management-порт (`GUARDRAILS_API_ADDR`) не
аутентифицирован и несёт мутирующие ручки правил и настроек, поэтому открывать
его внешнему вызывающему нельзя. Engine API слушает свой адрес и требует свой
bearer-токен.

## Конфигурация

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `GUARDRAILS_ENGINE_API_ADDR` | — | адрес engine-листенера; пусто — листенер выключен |
| `GUARDRAILS_ENGINE_API_TOKEN` | — | bearer-токен; **обязателен**, если адрес задан |
| `GUARDRAILS_DATA_PLANE_ENABLED` | `true` | `false` не поднимает gateway и снимает требование `GUARDRAILS_UPSTREAM_BASE_URL` |
| `GUARDRAILS_API_IGNORE_UNKNOWN_FIELDS` | `false` | `true` — management REST игнорирует незнакомые поля вместо 400 |

Компонентный деплой — только движок, без прокси и без upstream:

```sh
GUARDRAILS_DATA_PLANE_ENABLED=false \
GUARDRAILS_ENGINE_API_ADDR=:9100 \
GUARDRAILS_ENGINE_API_TOKEN=$ENGINE_TOKEN \
GUARDRAILS_STORE_BACKEND=redis GUARDRAILS_STORE_REDIS_ADDR=redis:6379 \
  ./guardrails-llm-filter
```

Состояние маскирования живёт в том же сторе, что и всё остальное
(`GUARDRAILS_STORE_BACKEND`), с тем же `GUARDRAILS_STORE_MASKING_TTL` и, если
включено, тем же шифрованием at-rest (`GUARDRAILS_STORE_ENCRYPTION_*`).
`GUARDRAILS_MASKING_TTL` должен превышать максимальное время между `/v1/mask` и
`/v1/unmask`.

## Авторизация

Каждый запрос к `/v1/mask` и `/v1/unmask` обязан несть
`Authorization: Bearer <GUARDRAILS_ENGINE_API_TOKEN>`. Сравнение — константное по
времени; токен никогда не логируется. Отсутствие или несовпадение → `401` с
`code=unauthorized` и заголовком `WWW-Authenticate: Bearer`.

`/v1/engine/version` намеренно без авторизации: он отдаёт только версию
контракта и билда, никаких данных.

## `POST /v1/mask`

```jsonc
// запрос
{
  "texts": ["оплату подтвердил Иванов Иван Петрович, почта a@b.c"],
  "correlation_id": "conv-42-turn-7",
  "data_types": ["personal_data", "credentials"]   // необязательно: номера или имена
}
```

```jsonc
// 200
{
  "correlation_id": "conv-42-turn-7",
  "masked_texts": ["оплату подтвердил <FIO_1>, почта <EMAIL_1>"],
  "placeholders": [
    { "placeholder": "<FIO_1>",   "rule_id": "pii.fio-ru", "data_type": "PERSONAL_DATA" },
    { "placeholder": "<EMAIL_1>", "rule_id": "pii.email",  "data_type": "PERSONAL_DATA" }
  ],
  "triggered_rule_ids": ["pii.fio-ru", "pii.email"],
  "triggered_data_types": ["PERSONAL_DATA"]
}
```

* `masked_texts` — ровно по одному элементу на каждый входной текст, в том же
  порядке. Если ничего не сработало, текст возвращается как есть.
* `placeholders` — что именно заменено, **без оригиналов**. Оригинал достаётся
  только через `/v1/unmask`, поэтому ответ на маскирование нельзя превратить в
  выгрузку секретов.
* `data_types` сужает область сканирования; пусто/отсутствует — все объявленные
  типы плюс `CUSTOM` (как у `/v1/scan`).
* Незнакомые поля запроса игнорируются: движок вызывается generic-шлюзом, чей
  payload может быть богаче этого контракта.

## `POST /v1/unmask`

```jsonc
{ "texts": ["ответ на <EMAIL_1>"], "correlation_id": "conv-42-turn-7" }
```

```jsonc
// 200
{ "correlation_id": "conv-42-turn-7", "texts": ["ответ на a@b.c"] }
```

Демаскирование идёт через тот же движок, что и data-plane (точные замены +
placeholder-regex), поэтому восстановление не зависит от реализации консьюмера.

## Ошибки

Тело любой ошибки — `{"code": "...", "message": "..."}`; `code` — часть
контракта, на него можно ветвиться.

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `invalid_request` | нет/пустой `correlation_id`, `correlation_id` длиннее 200 байт, битый JSON, пустое тело, незнакомый `data_types` |
| 401 | `unauthorized` | нет или неверный bearer-токен |
| 404 | `unknown_correlation_id` | состояния для этого `correlation_id` нет: не маскировали, истёк TTL, или id перепутан |
| 405 | `invalid_request` | метод кроме `POST` (с заголовком `Allow`) |
| 413 | `request_too_large` | тело больше `GUARDRAILS_MAX_REQUEST_BYTES` |
| 503 | `store_unavailable` | общий стор не записал или не отдал состояние |

Два решения приняты сознательно:

* **`/v1/mask` падает с 503, если состояние не записалось.** Иначе вызывающий
  получил бы замаскированный текст, который уже никогда не сможет
  размаскировать.
* **`/v1/unmask` не отражает текст как есть при неизвестном `correlation_id`, а
  отдаёт 404.** Молчаливый passthrough вернул бы плейсхолдеры пользователю
  вызывающего, а это уже утечка наружу.

## Границы контракта

* **Один `/v1/mask` на `correlation_id`.** Движок нумерует плейсхолдеры внутри
  вызова (`<EMAIL_1>` в каждом вызове начинает с единицы), поэтому повторный
  `/v1/mask` с тем же id **перезаписывает** состояние: восстановить текст,
  замаскированный предыдущим вызовом, уже не получится. Для нового обмена
  берите новый `correlation_id`.
* **Плейсхолдеры стабильны внутри одного ответа**, а не между вызовами.
* **Латентность.** Это не data-path: вызов делает полный скан текста и запись в
  стор. Вызывающий сам решает, как обрабатывать недоступность движка —
  сервис не подменяет решение вызывающего своим fail-open.
* **Режим `GUARDRAILS_MODE` (detect/enforce) здесь не действует**: вызов
  `/v1/mask` — это явный запрос на маскирование, теневого режима у него нет.
  `POST /v1/scan` остаётся инструментом консоли («Rule Tester»), для интеграции
  предназначен `/v1/mask`.

## Стабильность

Контракт версионирован и **стабилен отдельно от внутренностей консоли**.

* Текущая версия — `v1`, её отдаёт `GET /v1/engine/version` в поле
  `api_version`.
* Гарантия: в пределах `v1` мы можем **добавлять** поля в ответы и новые
  необязательные поля в запросы, но не удалять и не менять смысл существующих;
  новые значения `code` могут появляться, поэтому неизвестный `code` нужно
  обрабатывать как «ошибка вообще», а не падать.
* Ломающее изменение (переименование/удаление поля, смена типа, смена семантики
  `correlation_id`) означает новый префикс пути (`/v2/...`), а `v1` продолжает
  работать, пока не будет объявлено о снятии с поддержки в CHANGELOG.
* Код `internal/*` под этой ручкой менять можно свободно: стабилен контракт, а
  не внутренняя раскладка пакетов.
